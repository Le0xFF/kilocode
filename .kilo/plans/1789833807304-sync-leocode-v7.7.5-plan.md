# Sync upstream origin/main → leocode fino a v7.7.5 (ultima stable tag)

## Obiettivo

Portare il branch `leocode` in sync con l'upstream Kilo-Org/kilocode **fino alla stable tag `v7.7.5`** (sha `01ef456fe7f41aa1f7b8a4e6b545dd1e0fbeeceb`), senza integrare alcun commit oltre quella tag (il HEAD di `origin/main`, `a85ae672a3`, va esplicitamente escluso). Dopo il sync, l'estensione VS Code deve restare **interamente offline**: questo è un hard requirement verificato a ogni step dal guard `bun run check:offline` (invarianti I1–I10).

Sole la branch `leocode` viene modificata; la branch `main` (remote locale che punta a `origin/main`) resta intatta e serve solo come sorgente del merge.

## Analisi

### Stato attuale (verificato su repo)

- Remotes: `origin` = `https://github.com/Kilo-Org/kilocode/` (upstream), `main` = `https://github.com/Le0xFF/kilocode` (fork personale).
- Branch corrente: `leocode` (HEAD `1f8f4c7d`), working tree pulito.
- `leocode` è un fork pruned costruito su **v7.7.4** (`a3e508f7`): gli ultimi ~30 commit di Le0xFF sono il closeout del sync v7.7.4 + hardening offline (guard `check-offline-invariants.ts`, modelli locali `models-dev.local.json`, media-local, env sanitization in `server-manager.ts`, rimozione gateway/telemetry/marketplace/LSP/auto-update/session-sharing).
- Tag disponibili localmente fino a `v7.7.4`; `v7.7.5` esiste solo sull'origin (da fetchare).
- **Delta da integrare = `v7.7.4..v7.7.5`**: 42 commit non-merge + 1 commit di release (version bump + changelog, 228 righe). Totale 63 file, +2641/−541 righe.
- Concentrazione del delta: ~28 commit su `packages/kilo-vscode/` (Agent Manager: mentions `@model`/`@past-chats`/`@worktrees`, `NewWorktreeDialog`, recovery stalled permission approvals, regex escaping), ~7 su `packages/opencode/src/` (fix bash read-only commands, agent-switch reminders), 2 docs-only, ~5 altri pacchetti (kilo-ui, sdk/js hand-edited `permission.ts`).
- **Rischio superfici online nel range: zero** (scan esaustiva: telemetry/PostHog, gateway/auth/marketplace/KiloClaw, models.dev/provider catalog, auto-update, session sharing/cloud sessions, websearch-kilo-exa/generate-image, LSP/FIM, `$schema` app.kilo.ai → tutti untouched). Nessun file sotto `packages/opencode/src/server/` → **no rigenerazione SDK** (`script/generate.ts` non serve, salvo sorprese al dry-run).

### Componenti coinvolti / vincoli architetturali

- Procedura autoritativa: `docs/upstream-sync.md` (pre-condizioni, comandi esatti, matrice take-ours/take-theirs, I1–I10, rollback). Checklist operativa: `.kilo/skills/upstream-sync/SKILL.md`. Subagente dedicato: `.kilo/agent/upstream-sync.md` (esegue UNO step per volta: batch assegnato, risoluzione conflitti senza refactoring, marker `kilocode_change` vincenti, offline prevale su feature alignment, gate ordinati, report strutturato finale).
- Invarianti offline I1–I10 verificate deterministicamente da `script/check-offline-invariants.ts` (radice, `bun run check:offline`, exit 0 = ok): I1 `KILO_DISABLE_MODELS_FETCH` in `resolveManagedServerEnv` (chiamata allo spawn), I2 `urls=[]` in `session/network.ts` + early-return `"retry"` in `kilocode/session/processor.ts`, I3 provider hard-cut + `models-dev.local.json`, I4 route `/media-local/*` registrata, I5 env spawn sanificato (OTEL_/BUN_/NODE_OPTIONS/proxy/API keys/AWS_/VERTEX_), I6 workspace list esplicita 22 voci senza glob, I7 assenza kilo-gateway/kilo-telemetry + zero import live, I8 assenza kiloclaw/RemoteStatusService/MarketplacePanelProvider/autocomplete, I9 i18n 4 pool locale + test unused-keys, I10 allowlist 10 workflow.
- Guard aggiuntivi CI: `check:duplication` (+allowlist), `check-workflows`, `check-forbidden-strings`, `check-md-table-padding`, `check-kilo-generated-artifacts`.
- Test: SOLO `bun run test:unit` da `packages/kilo-vscode/` (runner anti-OOM); mai `bun test` dalla radice (exit 1 by design). Typecheck: `tsgo` (non tsc).
- Regola marker: nei file condivisi i blocchi `kilocode_change` vincono; in assenza di marker si preferisce sempre la versione che mantiene l'app offline. Nei path `kilocode`/pacchetti Kilo-owned i marker non servono.
- Rollback: backup tag locale `pre-sync-YYYYMMDD` (mai pushato); `git merge --abort` durante il merge, `git reset --hard <tag>` dopo.

## Assunzioni

1. `v7.7.5` è l'ultima stable tag pubblicata su origin (verificata via `git ls-remote --tags origin`: è la più alta tra i `vX.Y.Z` netti). Se durante l'esecuzione compaiono tag stabili superiori, il target resta comunque quello fissato al momento della pianificazione: **v7.7.5** — non estendere il sync oltre.
2. L'oggetto `01ef456f` non è ancora presente localmente: verrà recuperato con `git fetch origin main --tags` (step 1). Se il fetch non lo porta (es. tag annesso a un altro ref), si usa il parent `3a1e4964` (presente localmente) come fine-range: il commit di release aggiunge solo version bump/changelog.
3. Il diffstat del range (63 file, +2641/−541) è piccolo abbastanza da essere gestito in **un singolo merge**, senza bisogno di suddivisione in batch intermedi: il subagente upstream-sync può eseguire l'intero batch `v7.7.4→v7.7.5`. La suddivisione in step qui sotto è per *gate di verifica* sequenziali, non per frammentare il merge.
4. `bun` è disponibile sul sistema (`~/.bun/bin/bun`); nessun container/podman.
5. Nuovi dipendenze upstream che reintroducano surface online (ai-sdk, bonjour-service, AWS credential providers, sst/changesets) vanno **rifiutate** durante la risoluzione dei conflitti.
6. I baseline di visual-regression NON vengono mergiati pezzo per pezzo: vengono rigenerati una sola volta nello step di close-out, prima del packaging gate.

## Piano di implementazione

Il flusso è strettamente sequenziale: ogni step parte solo dopo il completamento (e approvazione utente) del precedente. Ogni step termina con codebase compilabile e guard verdi.

---

### Step 1 — Pre-condizioni, fetch e punto di rollback

**Obiettivo**: mettere il repo nelle pre-condizioni richieste dalla procedura ufficiale e creare il punto di rollback.

**Motivazione**: ogni comando successivo dipende da `main == origin/main`, dal fetch delle tag (inclusa `v7.7.5`) e da un tag di backup sicuro.

**File da leggere**: `docs/upstream-sync.md` (sezione pre-condizioni), `PRUNE-NOTES.md` (vincoli strutturali), `.kilo/skills/upstream-sync/SKILL.md` (punti 1–2).

**File da modificare**: nessuno.

**Attività**:
1. Verificare: branch corrente = `leocode`; `git status` pulito; remotes `origin` + `main` presenti; bun disponibile.
2. `git fetch origin` (recupera `origin/main` aggiornato + tag, inclusa `v7.7.5` = `01ef456f`).
3. `git switch main && git pull --ff-only origin main && git switch leocode` — portare la branch locale `main` al pari di `origin/main` (senza modificarla altrimenti).
4. Confermare: `git rev-parse main` == `git rev-parse origin/main` (atteso `a85ae672a3`); `git rev-parse v7.7.5` risolve a `01ef456fe7f41aa1f7b8a4e6b545dd1e0fbeeceb`.
5. Creare backup tag locale: `git tag -f pre-sync-$(date +%Y%m%d)` su `leocode` (mai pushato).
6. Dry-run del merge: `git merge-tree --write-tree --name-only $(git rev-parse v7.7.5) leocode > /tmp/kilo/conflicts.txt` (riga 1 = tree OID). Controllare l'elenco conflitti contro la matrice di `docs/upstream-sync.md`; annotare le sorprese (file fuori dalle categorie note) in un breve report.

**Output atteso**: repo pronto (main ff-updated, tag `pre-sync-*` creato, `v7.7.5` risolvibile), file `/tmp/kilo/conflicts.txt` con la lista conflitti prevista.

**Verifiche**: `main == origin/main`; tag esistente; output merge-tree ispezionato e classificato secondo la matrice; nessuna modifica al working tree.

**Compilazione**: n/a (nessun cambiamento al codice).

**Rischi**: se `v7.7.5` non arriva col fetch, usare il parent locale `3a1e4964` come fine-range (documentato nell'assunzione 2) e registrare la deviazione nel report.

**Istruzioni per il subagente**: esegui solo questo step; non anticipare il merge; non pushare nulla; se qualcosa delle pre-condizioni non regge, fermati e segnala invece di procedere.

---

### Step 2 — Merge di v7.7.5 in leocode, risoluzione conflitti, reinstall dipendenze

**Obiettivo**: eseguire `git merge v7.7.5` su `leocode`, risolvere tutti i conflitti secondo la matrice ufficiale, riapplicare le invarianti I1–I10 e reinstallare le dipendenze.

**Motivazione**: cuore del sync; tutto il resto (gate, smoke, closeout) presuppone un merge risolto.

**Esecuzione**: affidare questo step al **subagente `upstream-sync`** (`.kilo/agent/upstream-sync.md`), assegnandogli come batch unico il range `a3e508f7..01ef456f` (v7.7.4→v7.7.5, oppure `..3a1e4964` se il tag non è risolvibile). Il prompt deve includere: SHAs validati dal passo 1, il contenuto di `/tmp/kilo/conflicts.txt`, la regola "non integrare nulla oltre v7.7.5", e l'obbligo di produrre il report strutturato previsto dal suo definition.

**File da leggere** (dal subagente): `docs/upstream-sync.md` (primario), `PRUNE-NOTES.md`, skill upstream-sync, `/tmp/kilo/conflicts.txt`; poi i file in conflitto uno a uno.

**File da modificare**: solo quelli in conflitto, secondo la matrice:
- **take-ours / keep-deleted**: qualsiasi reintroduzione di package pruned (jetbrains, docs-site, console, sdk-next, session-ui, storybook, client, httpapi-codegen), nuovi file sotto `packages/kilo-gateway/**`, alberi i18n (poi importare solo chiavi nuove referenziate), `opencode/src/kilo-sessions/**`, `src/kilocode/{claw,event-service}/**`.
- **take-theirs**: `bun.lock` base (lo riconcilia `bun install`), `.github/workflows/*.yml` (verificare trigger validi + aggiornare `check-workflows.ts` solo se l'inventario cambia), `kilo-vscode/src/services/browser-automation/**`, `esbuild.js`, shared code (kilo-ui/core/indexing/tui/schema) salvo file toccati da marker.
- **union/manuale**: root `package.json` (mantenere la workspace list esplicita 22 voci; prendere gli script nuovi tipo `check:duplication`), `AGENTS.md` di radice (preservare sezione offline/pruned), `kilo-vscode/package.json` (aggiungere dipendenze browser legittime, scartare ciò che il fork ha rimosso).
- **marker-winning**: `opencode/src/provider/**` + `local-providers.ts` + `models-dev.local.json`; `opencode/src/session/**` (integrare drain/fork/status/compaction mantenendo I2).
- **riapplicazione speciale**: `packages/kilo-vscode/src/services/cli-backend/server-manager.ts` → take-theirs poi ricopiare `resolveManagedServerEnv` da `git show pre-sync-...:packages/kilo-vscode/src/services/cli-backend/server-manager.ts` (I1/I5).
- **nuovi `.changeset/*.md`** → eliminare (toolchain rimossa dal fork).
- **baseline PNG di visual-regression** → NON mergiare: annotarli nel report per la rigenerazione dello step 4.
- Rifiutare dipendenze online emerse dai conflitti (ai-sdk, bonjour-service, AWS credential providers, sst/changesets).
- Nelle aree del delta attese (mentions/worktree-dialog in `webview-ui/agent-manager/`, `kilocode/session/mode-reminders.ts`, `kilocode/tool/shell-pattern.ts`, `sdk/js/src/kilocode/permission.ts`): verificare che il merge non attivi surface remote (le modifiche sono UX/CLI, ma controllare i diff hunk-by-hunk).

**Attività** (ordine del subagente): merge → risoluzione conflitti → riapplicazione I1–I10 su ogni hunk risolto → `bun install` (riconcilia `bun.lock` con la workspace list esplicita; verificare che patchedDependencies si applichino e che gateway/telemetry non vengano riacquisite) → `script/generate.ts` **solo se** il dry-run avesse mostrato cambiamenti sotto `packages/opencode/src/server/` (atteso: no).

**Output atteso**: merge commit su `leocode` (commit message conforme: `chore: sync upstream v7.7.5 into leocode (offline fork)` o stile equivalente del fork), tree compilabile, report strutturato del subagente (conflitti, decisioni non ovvie, dipendenze aggiunte/rifiutate, evidenza per invariante, note per review).

**Verifiche**: `git status` pulito post-merge; `git rev-list --count leocode..v7.7.5` == 0 (sync completo fino alla tag); nessun file pruned reintegrato; `bun install` terminato senza errori.

**Compilazione**: `bun turbo typecheck` dalla radice deve passare a fine step; eventuali errori introdotti dalla risoluzione vanno risolti prima di chiudere (nessun refactoring extra).

**Rischi**: conflitti in file condivisi opencode senza marker (preferire offline); regressioni silenziose in Agent Manager (coperte dai test unitari dello step 3); lockfile che re-introduce dipendenze rimosse (bloccare in `bun install`).

**Istruzioni per il subagente**: solo il batch assegnato; la risoluzione dei conflitti è l'unico intervento consentito sul codice (zero refactoring/renaming); i marker `kilocode_change` vincono sempre sui file condivisi, in assenza di marker vince la versione offline; offline prevale su feature alignment — ogni feature online rifiutata/neutralizzata va documentata nel report; non mergiare baseline PNG sparsi; niente push/PR; fermarsi se il range non corrisponde a quanto assegnato (mai indovinare il delta).

### Step 3 — Gate di qualità: typecheck, lint, guard CI, test unitari, check:offline

**Obiettivo**: verificare che il merge non abbia rotto nulla e che tutte le invarianti offline tengano.

**Motivazione**: hard requirement offline + regressione tecnica: due famiglie di verifiche distinte, entrambe obbligatorie prima di dichiarare lo step fatto.

**File da leggere**: report dello step 2 (per i punti deboli segnalati).

**File da modificare**: solo fix mirate di errori introdotti dallo step 2 (mai refactoring).

**Attività** (ordine fisso):
1. Dalla radice: `bun run typecheck` (turbo/tsgo) e `bun run lint` (oxlint).
2. Guard CI dalla radice: `bun run script/check-workflows.ts`, `bun run script/check-forbidden-strings.ts`, `bun run script/check-md-table-padding.ts`, `bun run script/check-kilo-generated-artifacts.ts`, `bun run check:duplication` (se emergono duplicazioni nuove del merge, refactorizzare minimamente o giustificare nell'allowlist esistente — non allargare silenziosamente i limiti).
3. Dalla radice: `bun run check:offline` — deve uscire 0 (tutte I1–I10). Qualsiasi fallimento = invarianti violate dal merge: correggere riapplicando la categoria relativa della matrice.
4. Da `packages/kilo-vscode/`: `bun run typecheck` (sia src sia webview), poi `bun run test:unit` (runner anti-OOM; MAI `bun test` dalla radice). Focus atteso: test di Agent Manager (mentions, worktree dialog, permission recovery) e test CLI (shell-pattern, mode-reminders).

**Output atteso**: tutti i comandi a exit 0; eventuale lista di fix applicate per portarli a verde.

**Verifiche**: `check:offline` == 0; `test:unit` verde; typecheck/lint verdi; guard verdi.

**Compilazione**: implicita nel typecheck; se un test rivela un errore di runtime non coperto dal typecheck, fixarlo nello stesso step.

**Rischi**: test quarantenati pre-esistenti (uno era stato messo in quarantena nel closeout v7.7.4 in attesa di preference-plumbing): se ripresentano failure, valutare se il delta v7.7.5 le risolve (de-quarantena motivata) o mantenerle quarantenate con nota.

**Istruzioni per il subagente**: esegui solo i gate qui elencati; non riparare cose non rotte dallo step 2; ogni fix deve essere minima e tracciabile nel report; se `check:offline` fallisce, non procedere oltre finché non torna verde.

---

### Step 4 — Smoke test offline, rigenerazione baseline visive, packaging gate

**Obiettivo**: prova funzionale end-to-end che l'estensione/CLI restino completamente offline, più chiusura del gate di packaging.

**Motivazione**: `check:offline` verifica pattern statici; lo smoke test verifica il comportamento reale del backend spawnato. I baseline visivi vanno rigenerati dopo il merge (le UI di Agent Manager sono cambiate) prima del packaging gate.

**File da leggere**: `PRUNE-NOTES.md` (matrice percorsi online residui user-gated, righe 79–117), skill upstream-sync (punto 10: procedura smoke).

**File da modificare**: solo baseline PNG rigenerati (via tooling visual-regression del fork, con test-fixtures in `packages/kilo-vscode/test-fixtures/visual-regression/`) — mai edit manuali.

**Attività**:
1. **Smoke offline**: da `packages/opencode/` avviare `bun dev serve` (backend locale), poi `curl http://localhost:<port>/provider` — il catalogo deve mostrare **solo** provider locali/configurati: nessun `kilo`, nessun gateway, nessun modello da fetch remoto. Verificare anche che `KILO_DISABLE_MODELS_FETCH` arrivi all'env del child (log/dump env) e che il processo non apra connessioni esterne (nessun retry permanente da ECONNREFUSED grazie a I2). Al termine: kill del processo.
2. **Baseline visive**: rigenerare una sola volta i baseline di visual-regression di `kilo-vscode` (i PNG sparsi del merge erano stati messi da parte nello step 2) e far passare il confronto con i nuovi baseline.
3. **Packaging gate** (dal momento che `sdk/js/src/kilocode/permission.ts` è cambiato nel delta, anche se hand-edit): da `packages/kilo-vscode/` eseguire `bun run compile` (`prepare:cli-binary` + `prepare:sdk` + `build:check`).
4. Aggiornare la documentazione di stato del fork: `PRUNE-NOTES.md` / registro di sync in `docs/` con riga "sync fino a v7.7.5 completato" (stesso formato usato nel closeout v7.7.4).

**Output atteso**: smoke green (catalogo 100% locale), baseline rigenerate e confrontate, `compile` a exit 0, doc aggiornati.

**Verifiche**: output curl contiene solo provider locali; `bun run compile` verde; doc aggiornati; nessun processo residuo.

**Compilazione**: `compile` È la compilazione di packaging; deve passare.

**Rischi**: se lo smoke mostra un provider remoto nel catalogo, è una violazione I3/I1 → bloccare e tornare allo step 2/3 con fix mirata, non forzare avanti.

**Istruzioni per il subagente**: esegui solo questi controlli; non aggiungere feature; se lo smoke fallisce, fermati e riporta esattamente cosa appare in `/provider`.

---

### Step 5 — Commit finale del closeout, verifica di completezza, revisione utente

**Obiettivo**: chiudere formalmente il sync con verifica oggettiva di completezza e consegnare alla revisione.

**Motivazione**: definizione di "sync complete" della procedura: passi fatti con approvazione utente, `check:offline` 0, smoke green, delta a zero, nessuna superficie online riattivata, guard/test/compile verdi, doc aggiornati.

**File da leggere**: tutti i report degli step precedenti.

**File da modificare**: solo eventuale commit del closeout (doc + baseline) se non già committati nello step 4.

**Attività**:
1. Eventuale commit del closeout (baseline + doc) con messaggio `chore: record v7.7.5 sync completion in leocode` (stile del fork).
2. Verifica oggettiva di completezza:
   - `git rev-list --count leocode..v7.7.5` == 0 (nessun commit upstream ≤ v7.7.5 mancante);
   - `git rev-list --count v7.7.5..origin/main` > 0 **è atteso e corretto**: quei commit (tra cui il HEAD `a85ae672`) sono oltre l'ultima stable tag e devono restare esclusi;
   - `bun run check:offline` == 0; `check:duplication`, `check-workflows`, `check-forbidden-strings` verdi;
   - `git status` pulito; working tree senza file spuri.
3. Compilare il **report finale** per la revisione utente: conflitti risolti + decisioni, invarianti I1–I10 con evidenza, dipendenze aggiunte/rifiutate, risultati guard/test/smoke/compile, note sulle quarantene, dichiarazione esplicita "nessun commit oltre v7.7.5 integrato".

**Output atteso**: branch `leocode` definitivamente sync fino a v7.7.5, interamente offline, pronta per la revisione dell'utente.

**Verifiche**: i quattro punti sopra; consegna del report.

**Compilazione**: già garantita dagli step 3–4; rilettura finale `git status` + `check:offline`.

**Rischi**: nessuno tecnico residuo; se l'utente trova problemi in revisione, la correzione passa da un nuovo step mirato (il tag `pre-sync-*` resta come rollback totale).

**Istruzioni per il subagente**: non integrare nulla oltre v7.7.5 in nessuna circostanza; non pushare; il deliverable è il report, non ulteriore codice.

---

## Criteri di completamento

- Tutti gli step sono stati completati in ordine, ciascuno approvato dall'utente prima del successivo.
- `git rev-list --count leocode..v7.7.5` == 0: sync completo fino all'ultima stable tag, né un commit oltre.
- `bun run check:offline` exit 0 (invarianti I1–I10) + smoke `/provider` con soli provider locali: l'estensione resta intermente offline (hard requirement soddisfatto).
- Typecheck, lint, guard CI (workflows, forbidden-strings, md-table-padding, generated-artifacts, duplication), `test:unit` di `kilo-vscode`, `compile` packaging: tutti verdi.
- Nessuna funzionalità extra introdotta; nessun refactoring non richiesto durante la risoluzione dei conflitti.
- Doc di stato del fork aggiornati; tag di rollback `pre-sync-*` conservato localmente.
